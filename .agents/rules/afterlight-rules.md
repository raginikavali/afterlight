# AFTERLIGHT PROJECT RULES

1. BUILD THE PRODUCT, NOT A GENERIC LANDING PAGE.
2. The core story is CITY → CLOCK → SPACE → CAPACITY → MATCH → TRUST → PILOT.
3. The city visualization must be state-driven and interactive.
4. Time must drive the actual simulated data and visual states.
5. Matching must use deterministic local logic, not a fake “AI found a match” animation.
6. Invalid matches must explain the blocking condition.
7. Human/operator review must remain explicit.
8. Amber light represents available capacity; do not dilute this metaphor with many accent colors.
9. Avoid purple AI gradients, stock imagery, robot imagery, generic SaaS cards, fake testimonials, fake logos, fake results, and unnecessary dashboards.
10. Motion must communicate cause/effect. Prefer subtle architectural transitions over spectacle.
11. Keep the page focused. Do not add authentication, billing, backend infrastructure, blogs, or unrelated routes.
12. Responsive behavior must be deliberately redesigned for touch, not merely scaled down.
13. Support keyboard interaction, focus states, semantic structure, and reduced motion.
14. Run and inspect the actual application. Do not assume correctness from compilation.
15. Fix console errors, broken interactions, overflow, visual regressions, and accessibility issues before declaring completion.
16. If implementation becomes difficult, simplify implementation complexity rather than simplifying the intended user experience.
17. Never claim simulated numbers are real.
18. Never fabricate the required “AI was wrong/weak” assignment note. Record a real issue encountered during development if one occurs.
